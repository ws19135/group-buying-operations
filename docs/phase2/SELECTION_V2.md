# SOP 02 選品評分 V2 規格（可驗證條件＋證據＋系統計算）

> 狀態：**提案規格**。所有權重、門檻、樣本數都是「建議值，待 Owner 核准」（`approved=false`），不是公司正式制度。
> 範圍：只升級 SOP 02 的「商品選品評估」評分；不改商品審核流程與 G1–G5 的核准權限；SOP 01 適配、SOP 03 試用與可行性仍是獨立模組，這裡只**讀取**它們。
> 相關：[PRODUCT_SELECTION_TRIAL.md](PRODUCT_SELECTION_TRIAL.md)（V1 設計）、[../biz-model/04-FINANCE_AND_COMMISSION.md](../biz-model/04-FINANCE_AND_COMMISSION.md)（三種商業模式的利潤口徑）、[SELECTION_V2_ROLLBACK.md](SELECTION_V2_ROLLBACK.md)（相容與回滾）。

## 1. 為什麼要改（V1 的問題）

V1 是六個維度各給 1–5 分的主觀評分，只有「理由文字」與「證據數量」。問題：同一商品不同人會給不同分、理由難以覆核、已有的系統資料（適配、價格、可行性、廠商調查、試用、歷史訂單）沒有被利用。

V2 的原則：**分數由「可驗證的子條件」算出來，不是人憑感覺給**。

## 2. 設計原則

1. 100 分制、六維度與原始建議權重不變：客群需求符合度 25、商品品質與安全性 25、利潤與價格競爭力 20、供應商履約能力 15、內容展示與說服力 10、複購潛力 5。
2. 每個維度由多個**子條件**組成；子條件的權重在維度內合計 100。
3. 子條件有四種型別：`BOOL`（是／否）、`NUMBER`（數值，越高越好或越低越好）、`BAND`（落在區間內最好）、`ENUM`（選項對應分數）。
4. 每個子條件的答案只有四種狀態：**已知**、**未知**、**不適用（需原因）**、**自動取得**（系統從既有資料算出）。
5. **未知不是 0 分**：未知的子條件從分母排除，並降低資料完整度與可信度（與 V1 相同）。
6. **不適用需原因且受規則限制**：只有目錄標明「可不適用」的條件才能選不適用，且必須符合其不適用規則（例如「非受規範品類」）；系統若偵測到商品可能受規範，就不允許對相關條件選不適用。不適用的權重占維度超過上限時，標示需覆核並把可信度壓到「中」以下。不可任意排除低分項目。
7. **有可信資料就自動算，沒有就要求補件**；系統不捏造數值。自動值會保存「來源、參照編號、取得時間、樣本數」的快照。
8. **合規、重大安全與必要資格是獨立的硬性檢查**：不被總分抵銷；高分不代表通過。
9. **分數只是建議**：不核准商品、不核准 G1（選品核准）、不改任何狀態（沿用 V1，並有測試）。
10. **規則版本化**：送出時保存規則版本與設定快照、每個子條件的答案與來源快照；已送出的評估永遠以當時的規則顯示，不會被新規則悄悄改寫。

## 3. 計算方式

### 3.1 子條件分數（0～1）

| 型別 | 答案 | 分數 |
|---|---|---|
| `BOOL` | 是／否 | 1／0 |
| `NUMBER`（越高越好） | 數值 x，門檻 `floor`、`target` | x ≥ target → 1；x ≤ floor → 0；中間線性：(x − floor) ÷ (target − floor) |
| `NUMBER`（越低越好） | 同上，`target` < `floor` | x ≤ target → 1；x ≥ floor → 0；中間線性：(floor − x) ÷ (floor − target) |
| `BAND` | 數值 x，最佳區間 `[lo, hi]`，容忍 `tol` | x 在區間內 → 1；區間外每超出 1 單位扣 1 ÷ tol（最低 0） |
| `ENUM` | 選項 | 目錄內每個選項對應的分數（0～1） |

### 3.2 維度與總分

```
維度分（0～100）= 100 × Σ(子條件權重 × 子條件分數) ÷ Σ(已知且適用的子條件權重)
維度資料完整度   = Σ(已知且適用的權重) ÷ Σ(適用的權重)          （未知拉低，不適用排除）
總分（0～100）   = Σ(維度權重 × 維度分) ÷ Σ(有已知資料的維度權重)   （整個維度未知＝從分母排除）
資料完整度       = Σ(維度權重 × 維度資料完整度) ÷ Σ(全部維度權重)
證據完整度       = 「要求證據且已有答案」的子條件中，已有有效證據（或系統自動取得）的比例；沒有這類子條件時為 1
```

### 3.3 可信度與建議

- 可信度 `HIGH`：資料完整度 ≥ 高門檻 **且** 證據完整度 ≥ 0.8；`MEDIUM`：資料完整度 ≥ 中門檻 **且** 證據完整度 ≥ 0.5；`LOW`：資料完整度 ≥ 最低完整度；其餘 `INSUFFICIENT`。不適用占比超限時最高只到 `MEDIUM`。
- 建議（與 V1 同一組代碼，舊畫面可直接讀）：
  1. 合規「未通過」或任一**硬性條件為「否」** → `BLOCKED`（不論總分）。
  2. 資料完整度 < 最低完整度 或 沒有任何已知資料 → `INSUFFICIENT_DATA`。
  3. 總分 ≥ 進入商務審查門檻，且合規「通過」、沒有硬性條件為「未知」、可信度不是 `LOW`、沒有證據缺口 → `PROCEED`（**建議進入商務審查**，不是核准）。
  4. 總分 ≥ 補測門檻 → `SUPPLEMENT`（含：合規未查核／需法務、硬性條件未知、證據缺口等「最多只能補件」的情況）。
  5. 其餘 → `HOLD`。
- 證據缺口：有答案、目錄要求「必要證據」、卻沒有有效（未過期）證據的子條件；列出來，並阻止 `PROCEED`。

### 3.4 手動答案與自動值的衝突

- `source=AUTO` 的子條件只能由系統取得，不接受手填（避免繞過）。
- `source=EITHER` 的子條件：有可信自動值時以自動值為準（手填會被拒絕並說明）；沒有自動值時才可手填，手填且要求證據的必須掛證據。
- `source=MANUAL` 的子條件：只能手填。

## 4. 三種商業模式的利潤口徑

利潤維度必須區分商業模式（模式代碼沿用 biz-model：`AGENCY` 代營運、`KOL_CPS` KOL／KOC、`MOM_GROUP` 團媽／社群主）。**V2 不新增任何金額公式**：利潤指標一律讀取 SOP 03 商業可行性試算已經算好的結果（`contributionMarginPct`、`takeRatePct`、`companyContribution`，口徑為 biz-model 04 §2.2 的代理人口徑）；評估只決定「用哪個模式的門檻來判定好壞」。

| 模式 | 公司收益來源 | 團主／KOL 分潤 | 利潤維度的判讀重點（門檻為提案） |
|---|---|---|---|
| `AGENCY` 代營運 | 向品牌收服務費 | 視合約由公司或品牌付 | 抽成率與貢獻利潤率；分潤若由公司付則已含在貢獻利潤中 |
| `KOL_CPS` KOL／KOC | 向品牌收推廣分潤（可抽差額）或固定合作費 | 付給 KOL 屬公司成本 | 貢獻利潤率要求較高（內容與行銷費高），且必須為正 |
| `MOM_GROUP` 團媽 | 向品牌收分潤，或公司對團主分潤差額 | 付團主；團主自留價差時公司無此成本 | 貢獻利潤率門檻較低，但要求有可行性試算且分潤付款方已確認 |

- 未選商業模式 → 利潤維度的模式相關子條件為「未知」（不套用任何預設）。
- 沒有該商品的可行性試算 → 利潤子條件為「未知」，並產生「請建立商業可行性試算」的補件提示；**不用 SKU 成本自行推算貢獻利潤**。
- 毛利率（團購價與成本價的 SKU 毛利）只是參考條件，不含分潤與費用，權重較低。

## 5. 敏感資訊保護

- 利潤維度的子條件（成本、毛利、貢獻利潤、抽成率、分潤付款方）標為**敏感**：沒有 `product.cost.read` 的角色只看到「已知／未知／不適用」狀態與「資料已涵蓋」，**看不到數值、子條件分數與資料來源細節**。
- 這些子條件**全部是自動取得**，營運小編不能手填（避免手填洩漏或偽造）。
- 稽核紀錄的前後值只存「條件編號與狀態」，敏感數值不寫入稽核（沿用 V1 做法）；`v2_result` 內的敏感欄位在 API 回應依權限遮蔽。
- 維度分數與總分會含利潤維度（決策建議值），不視為成本原值；此為已知限制，列於「待 Owner 決策」。

| `skus` | 啟用中 SKU 的原價、團購價、成本價 | 成本價屬敏感 |
| SOP 03 `feasibility_scenarios` | 最新一筆的 `results.contributionMarginPct`／`takeRatePct`／`companyContribution` 與 `sources` | 只讀；不重算金額 |
| 廠商調查 `vendor_dd_records`／`vendor_dd_items` | 狀態、有效期、12 題狀態與非敏感條款欄位（交期、庫存政策、授權期限） | **不讀分潤與排他條款（第 10、11 題敏感欄位）** |
| SOP 03 `product_trials` | 最新已結論的資格試用結論 | 只讀 |
| `orders`／`order_items`／`refund_requests`／`service_cases`／`shipments` | 歷史退款率、客訴率、準時出貨率、回購率 | 只取聚合數字與樣本數；有最小樣本門檻 |

每個自動值保存：`value`、`sourceLabel`、`sourceRefs`（編號清單）、`asOf`、`sampleSize`。草稿顯示即時值；送出後顯示保存的快照。

**適用的廠商調查怎麼挑**（G1 決策摘要與 V2 自動取值共用同一規則，`pickDdRecord`）：0 商品專屬且已核准、未被取代 → 1 商品專屬且已退回／撤銷，或含法務封鎖項（明確的否定決定仍要看得見）→ 2 廠商層級且已核准、未被取代 → 3 商品專屬的草稿／審查中（進行中的作業，**不能蓋過**已核准的廠商層級調查）→ 4 其餘；同級取最新。已核准但到期或證據過期的調查仍會被選到，讓過期風險被看見。

## 8. 資料模型（migration 016，皆為「新增」，不改既有欄位語意）

- `product_evaluations` 新增：`rubric_version int`（`NULL`＝V1 舊制、`2`＝V2）、`commerce_model text`、`v2_input jsonb`（每個子條件的人工答案、不適用原因、證據編號）、`v2_result jsonb`（維度分、子條件結果與自動值快照、硬性檢查結果、證據完整度、不適用占比、旗標）。V2 評估仍填 V1 已有的 `total_score`／`completeness`／`confidence`／`recommendation`／`evidence_gaps`／`config_version`／`config_snapshot`，所以既有列表、G1 摘要、覆核流程不必改。
- `product_evaluations_guard()` 觸發器擴充：已送出的評估不可改 `rubric_version`、`commerce_model`、`v2_input`、`v2_result`。
- 新表 `evaluation_supplement_requests`：主管提出的補件要求（評估、子條件、說明、狀態 OPEN／DONE／CANCELLED、提出人與時間、處理人與時間）；不可實體刪除。
- 設定 `selection.scoring.v2`（`system_settings`，版本化）：維度權重、子條件權重覆寫、門檻、各模式利潤門檻、最小樣本、不適用占比上限、證據完整度門檻、`approved` 旗標、`enabled` 旗標（false＝新評估改建 V1）。**預設 `approved=false`**，儲存需 `selection.config` 權限並寫稽核；API：`GET／PUT /api/selection/config-v2`（尚無專用畫面）。
- 舊版（V1）評估：`rubric_version` 為 `NULL`，欄位與顯示完全不變，不重算、不遷移。
- 回滾策略見 [SELECTION_V2_ROLLBACK.md](SELECTION_V2_ROLLBACK.md)。

## 9. 流程與權限

- 建立評估預設為 V2；既有 V1 草稿可以繼續以 V1 編輯與送出；V1 已送出的評估原樣唯讀。
- 編輯／送出：`selection.write`；覆核（採用／不採用／需補資料）與提出補件要求：`product.review`（沿用）。
- 覆核「需補資料」時可針對個別子條件提出補件要求；補件要求不會改變評分；對該商品建立新版評估並送出後，OPEN 的要求由處理人標為 DONE。
- 評估與覆核都**不**改商品審核狀態、**不**核准 G1；G1 決策摘要只讀取現行評估的結果，且 `gateImpact` 恆為 `NONE`。

## 10. UI

- **選品評估編輯**：依六維度分組的子條件清單；每列顯示標籤、說明、答案控制（是／否／未知／不適用＋原因、數值、選項）、自動值與來源（可展開）、證據欄、缺資料原因；上方即時顯示總分、資料完整度、證據完整度、可信度、硬性檢查與建議（皆為預覽，送出才保存）。
- **覆核**：唯讀顯示各子條件與來源快照、不適用清單；可「提出補件要求」（針對子條件）與一般覆核決定。
- **廠商合作資格審查**：12 題進度條、缺件／風險／到期文件摘要；每題可直接展開編輯；顯示核准狀態與歷史版本。
- 沿用既有設計系統、圖示與角色權限；畫面上的英文縮寫保留並附中文。

## 11. 測試與驗收

- 單元：每種型別的分數公式與邊界、未知／不適用排除、不適用規則、硬性條件、完整度與可信度、建議階梯、權重驗證。
- 整合（真實 PostgreSQL）：自動取值、樣本不足、敏感遮蔽、權限、新舊相容、版本快照不被改寫、補件要求、G1 不被影響。
- E2E：建立 V2 評估 → 自動值 → 手填 → 證據 → 送出 → 覆核與補件；廠商 12 題進度。
- 突變驗證：刻意弄壞公式、遮蔽、不適用規則、快照，確認測試變紅。

## 13. 廠商 12 題的修補（與 V2 同一批交付）

12 題本身（目錄、結構化欄位、責任方與負責人、證據、狀態、送審核准、G1 唯讀摘要）早已實作，**沒有新建第二套資料表**。逐項盤點後修補：

| 項目 | 修補 |
|---|---|
| 敏感類別（分潤條款）的自由文字外洩 | 不適用原因、風險說明、法務說明與備註，沒有成本權限者一律看到占位字 |
| 授權期限沒有檢查 | 第 1 題 `authorizationValidUntil`、第 9 題 `licenseValidUntil` 過期＝不可送審、不可核准，核准後過期＝核准失效；快到期列入「即將到期」；標為不適用的題目不檢查 |
| 調查挑選順序錯誤 | 見 §7 的 `pickDdRecord`（商品專屬草稿不再蓋過廠商層級已核准調查） |
| 已確認的項目事後改條款 | 確認作廢、退回待補件（條款內容沒變則維持已確認） |
| 審查中證據仍可增減 | 與項目欄位一致：只有草稿與被退回時可增減；審查中先撤回 |
| 沒有「撤回送審」 | 新增：送審的人或有覆核權限者可把「審查中」撤回成草稿（稽核 `selection.dd.withdraw`） |
| 沒有版本鏈 | 新版核准後，同廠商同範圍先前已核准的調查標記為被取代（讀取時失效），新版記錄 `supersedes_id` |
| 沒有「沿用」 | 建立新版時可指定 `copyFromId`：帶入條款、責任方、負責人；項目一律回到待補件、不複製證據與確認；沒有成本權限者不會沿用出分潤條款 |
| 沒有 12 題進度與逐題缺件 | 回傳 `progress`（已確認＋不適用 ÷ 12）與 `perItem`（每題狀態、缺證據、證據與授權到期）；廠商頁、調查頁、G1 摘要都顯示 |

**不在這次範圍（列入 Owner 決策）**：職責分離、「已接受風險」狀態、涵蓋範圍、到期前提醒。
