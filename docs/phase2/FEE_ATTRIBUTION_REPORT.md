# 費用歸屬對照報告（Owner 決策 K-8）

> 狀態：**已建置（唯讀）**。位置：財務 → 「財務口徑核對」→ 分頁「費用歸屬對照」；API：`GET /api/reconciliation/fees`（可帶 `?campaignId=`）。
> 本階段**維持 KPI 試算與正式結算分離**：不修改結算、不入帳、不付款、不開發票；歷史資料回填、已確認結算更正、實際付款都需另案核准。
> 權限：`finance.read` ＋ `product.cost.read`。程式：`lib/fee-attribution.ts`（純函式）、`modules/finance-comparison.ts`、`tests/unit/fee-attribution.test.ts`（8 項）、`tests/finance-comparison.test.ts`（K-8 兩項）。

## 1. 盤點：現行費用負擔方資料與結算規則

| 費用 | 試算／KPI 側（商業可行性條款） | 正式財務側 | 結算是否處理 |
|---|---|---|---|
| 團主佣金 | 比例、基礎、**付款方**（公司／品牌） | 財務「分潤規則」（費率、規則版本、期間）；結算明細保存費率與規則版本快照；可覆寫與調整項（需原因） | ✅ 處理金額與費率；**不記錄付款方** |
| 公司服務費（品牌端） | 比例＋固定額、基礎 | 無（沒有對應欄位） | ❌ |
| 運費 | 每單金額、**負擔方** | `expenses`（類別 `SHIPPING`：檔期＋金額＋日期；**沒有負擔方、沒有實際付款方、沒有商品**） | ❌ |
| 平台及金流費 | GMV 比例或每單、負擔方 | `expenses`（`PLATFORM_FEE`，同上） | ❌ |
| 退款及退貨處理成本 | 每筆處理成本、負擔方（K-3 新增） | **沒有對應類別**；退款申請（`refund_requests`）是退給買家的款項，不是處理成本 | ❌ |
| 其他變動成本 | 每單金額、負擔方 | `expenses`（`OTHER`、`SAMPLE`、`MARKETING` 無法與試算項目逐項對應） | ❌ |
| 固定費用 | 金額、負擔方 | 同上，無對應 | ❌ |
| 收款方 | 收款模式（品牌自收／公司代收居中／團主代收） | `payments`（入帳／付款，人工紀錄，可關聯結算明細；不執行任何金流） | — |

**結算（`settlements`）目前只計算團主佣金**：歸因有效淨銷售額 × 財務規則費率，另有覆寫與調整項；不處理運費、平台費、退款退貨處理、固定費用、公司服務費。

## 2. 報告內容（每個「檔期 × 商品」）

每個費用項目列出：

1. **試算（KPI）採用的負擔方、金額（依實際訂單與條款計算）、條款來源是否已確認、條款版本**；
2. **財務已記錄的支出**（類別合計與筆數）；
3. **正式結算是否處理**；
4. **是否一致**：一致／**KPI 與正式結算尚未一致**／資料不足，並列出原因（結算未處理、支出無負擔方與付款方、暫估來源、多商品無法歸屬…）；
5. **可能的應收／應付**與「需確認什麼」（見 §3）。

報告頂端彙整「KPI 與正式結算尚未一致的費用項目」（各出現幾組）與未來整合方案文件連結。

## 3. 可能產生公司應收或應付的情形（只說「可能」，不入帳）

| 情形 | 結論 | 需要確認 |
|---|---|---|
| **收款：品牌自收** | 公司的服務費要向品牌收取 → 公司**可能有應收** | 服務費結算與開票時點、品牌付款條件 |
| **收款：團主代收** | 款項先在團主端，服務費需由代收款項取得 → 公司**可能有應收** | 團主回款時點、對帳方式 |
| **收款：公司代收居中** | 代收款是**負債（應付品牌貨款）**，不是公司收入；服務費可直接扣留 | 撥付品牌的時點 |
| **團主分潤付款方＝公司** | 公司對團主有**應付佣金**（結算已處理金額） | 付款時點與方式（系統只記錄入帳） |
| **團主分潤付款方＝品牌** | 若公司先行支付團主 → 公司**可能對品牌有應收** | 實際由誰付款、品牌是否同意償還 |
| **費用負擔方＝品牌／團主，但財務已記錄同類支出** | 若為公司墊付 → 公司**可能有應收** | 支出是否由公司墊付、對方是否同意償還、支出需標明所屬檔期與商品 |
| **費用負擔方＝品牌／團主，財務沒有支出紀錄** | **無法判斷** | 實際付款方 |
| **費用負擔方＝公司** | 公司成本；若實際由品牌或團主先付 → 公司可能有應付 | 實際付款方是否就是公司 |
| **未設定收款方或負擔方** | **無法判斷（缺資料）** | 補設定 |

> 系統**沒有記錄「實際付款方」**（`expenses` 只有類別、金額、日期），所以上述只能是「可能」。是否真的形成應收／應付，需財務依合約與實際付款確認。

## 4. 保留的合約版本、費用來源與差異原因

- **合約版本**：每份報告帶可行性版本與編號；分潤條件另見「分潤口徑差異核對」（合約版本）。
- **費用來源**：每個項目標示條款來源種類（合約／正式商務條件／廠商報價／試用實際／歷史資料／人工估計）與是否已確認。
- **差異原因**：每個「尚未一致」項目都有文字原因（見 §2-4）。

## 5. 唯讀的證據

- 報告呼叫前後 15 張相關資料表的筆數不變（測試驗證）。
- 測試案例：運費 60 × 6 張有效訂單＝360（KPI 側），財務已記錄 700 元運費 → 「KPI 與正式結算尚未一致」、可能對品牌有應收；退款申請不被當成退款處理成本；多商品檔期金額不估算。
- 結算演算法與 G1–G5 沒有任何改動。
