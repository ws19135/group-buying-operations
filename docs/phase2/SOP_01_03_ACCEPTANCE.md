# SOP 01～03 功能驗收與缺口補強（逐項矩陣）

> 驗收方式：**以程式、migration、API 路由、畫面與權限實際驗證，不採信 README**。所有資料皆為虛構 `[DEMO]`／`[E2E]`；未動正式資料、未啟用金流、未發送真實通知、未部署正式環境。
> 分類：✅ 已建置且驗證通過／◐ 已建置但操作體驗待改善／🟡 部分完成／⛔ 尚未建置／❓ 需要 Owner 決策。

## 1. 結論

- SOP 01、SOP 02 V2、SOP 03 的主要功能**都已建置**，沒有重建任何既有模組。本次補的是缺口：8 項小規模測試團 KPI、團主再次合作意願欄位、V2 最小設定畫面，以及驗收中發現的 **2 個資料外洩、2 個畫面缺陷**（見 §4）。
- 新增 **全流程 UI 驗收腳本** `scripts/e2e-flow.ts`（34 項檢查全過（其中 K-1～K-3 相關 7 項））：從新廠商、新商品、新團主開始，**全程只用畫面**，走完客群建檔 → 商品適配 → 選品 V2 → 廠商 12 題 → 商品試用 → 商業可行性 → G1 審核查閱 → V2 設定，沒有手動 API 或資料庫操作。
- 仍待 Owner 決定的是**政策與口徑**（門檻、導購觸及資料來源、實際利潤歸屬、覆核權限），已集中在 §6；程式沒有替 Owner 決定。

## 5. 已知但未動的項目

- `OPS_EDITOR` 沒有成本權限，不能確認敏感的「預估毛利」檢核。這是權限設計（分離職責）的結果，不是錯誤；建議之後在畫面補一句「需有成本權限者填寫」（本次未做，未逐一驗證現有錯誤訊息的文字）。
- 可行性「實際值回寫」（`recordActuals`）的口徑與 `lib/kpi.ts` 不同：**沒有改**（涉及金額公式，CLAUDE.md 規定先問 Owner）；KPI 卡因此不算實際貢獻利潤。
- 試用／廠商調查的覆核權限沿用既有設計，未更動。

## 7. 下一階段建議

1. 開始累積小規模測試團資料：每檔用畫面填「觸及與導購資料」，並確認可行性條款的來源為合約／正式商務條件，這樣 CVR 與每單貢獻利潤才會有值。
