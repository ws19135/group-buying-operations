### 7.2 D-39：營運小編資料範圍、承辦與交接（migration 029）

- **資料模型**：`collaboration_assignments`（目前承辦：`PRIMARY` 一案一位、`CO_OWNER` 共同承辦；結束用 `ended_at`，不實體刪除）、`collaboration_handovers`（append-only 交接紀錄，交接／釋出／整批交接必須有原因，資料庫 CHECK 強制）。`owner_user_id` 保留為「目前主要承辦」的顯示欄位，**資料範圍一律以 `collaboration_assignments` 為準**。migration 把 028 已有的 `owner_user_id` 回填為正式指派；沒有承辦人的不猜。
- **範圍**：系統管理者、營運主管看全部；營運小編只看自己承辦或被指派共同承辦；團主、廠商不變；財務仍為零。`campaignScope` 及其他模組的範圍**完全未改**（有測試固定）。
- **沒有人承辦的案件不會消失**：「沒有有效主要承辦人」＝沒有進行中的 `PRIMARY`，**或** 主要承辦人已停用／刪除（離職忘了交接也算）。這些案件進**待指派佇列**（`GET /collaboration/unassigned`）：營運主管看得到並可指派；營運小編看得到**非個資摘要**（單號、團主、廠商、商品、狀態、等待天數）並可**自行認領**——認領前讀不到案件內容與收件資料（404）。
- **端點**：指派／交接（需新權限 `collaboration.assign`，管理者與主管）、認領、釋出、加入／移除共同承辦（主管或目前主要承辦本人）、整批交接（離職）、交接紀錄。
- **預設行為**：小編建立或匯入的案件預設自己承辦；主管建立且沒指定承辦人的、團主或廠商自助建立的，進待指派佇列。
- **不產生通知**（D-41）：指派、交接都不寫 `notifications`（測試固定各表列數不變）。

### 7.3 D-40：個資保留與清除（政策衝突分析與機制）

**暫定政策**：核准日起 90 天；送達後依最後寄送日起 30 天；取較早到期日。

**衝突分析（實際推演 `computeRetentionUntil` 與清除流程）**

| # | 情境 | 舊行為 | 問題 | 處置 |
|---|---|---|---|---|
| C1 | 送達後 30 天已到期，但**補寄尚未寄出** | 到期即清除 | 補寄沒有地址可寄 | `evaluatePurge`：履約未結束 → **延後**（`SKIPPED_FULFILMENT`），下一輪再評估 |
| C2 | 核准後 90 天已過，但**首次樣品還沒寄出** | 到期即清除 | 廠商永遠寄不出去 | 同上延後 |
| C3 | 已寄出但團主**尚未確認收件**／樣品**退回**尚未決定補寄／申請**暫緩中** | 到期即清除 | 履約與爭議處理中資料消失 | 同上延後 |
| C4 | 補寄建立後，保留期被重算回「核准＋90」，但那天早已過去 → 立刻變成已過期 | 一建立補寄就被視為過期 | 廠商讀不到、又被清掉 | 以「履約是否結束」而不是日期單獨決定；廠商在履約未結束時仍可取得地址，直到硬性上限 |
| C5 | 履約一直不結束（延後無上限） | （舊版沒有延後） | 「延後」會變成無限期保留 | **硬性上限：核准後 180 天**一律強制清除（`PURGED_HARD_CAP`），廠商讀取也在 180 天後拒絕（不依賴排程） |
| C6 | 爭議、客訴、退款、法定保存義務 | 無機制，只能「不要按清除」 | 沒有依據、沒有期限、沒有稽核 | **保留例外**（`collaboration_retention_holds`）：事由代碼＋**依據**（≥10 字，不可含個資）＋**到期日（最長 365 天，資料庫 CHECK）**；到期自動失效、可提前解除；建立、解除都寫稽核；只阻止清除，**不擴大任何人的讀取權限** |
| C7 | 被拒絕／取消的申請，其收件資料 | 沿用建立日＋90 天 | 沒有被核准的資料為何要留 90 天？ | **未改**（政策空白，列為待決：O-D40-1） |
| C8 | 改地址後的舊資料、匯入暫存列 | 永遠不清（SF-1、SF-2） | 見上 | 已修正 |

**機制**：`runRecipientPurge`（`modules/collaboration-retention.ts`）——每次執行寫 `collaboration_purge_runs`（狀態 `SUCCEEDED／PARTIAL／FAILED`、各項計數），逐筆結果寫 `collaboration_purge_items`（`PURGED／PURGED_HARD_CAP／SKIPPED_HOLD／SKIPPED_FULFILMENT／FAILED／WOULD_PURGE`，只寫原因與錯誤碼，**不寫個資**，append-only）；單筆失敗不回滾整批、不被吞掉（記 `FAILED`、整體 `PARTIAL`）；支援**試跑（dry run）**；非試跑只有系統管理者。清除也處理匯入暫存列與錯誤紀錄。**監控**：`GET /collaboration/retention/status` 與畫面 `/collaboration/retention`（營運主管、管理者）回報已到期數、逾期超過 7 天的積壓、上次執行結果、生效中的保留例外，`alerts` 為 `NEVER_RUN／LAST_RUN_FAILED／OVERDUE_BACKLOG`——**本系統不自動發通知**，需由人或外部監控定期查看。

**排程邊界（Owner 授權前不得啟用）**：本系統**沒有任何 cron、worker 或 workflow 會呼叫清除**（`worker.ts`、`automation.ts`、`.github/workflows/*`、`docker-compose.prod.yml`、`render.yaml` 都有測試確認不含）。清除只能由人工按鈕、API 或 `npm run collab:purge`（預設試跑，要加 `--execute`）觸發；腳本在 `APP_ENV=production` 時**直接拒絕**，除非設定 `COLLABORATION_PURGE_PRODUCTION_AUTHORIZED=yes`（只有 Owner 書面授權後才可設定；有突變測試 M19）。開發排程與隔離環境驗證可以進行。

### 7.4 備份中的個資（評估與建議；未動任何備份）

| 項目 | 現況（由 repo 檔案確認） | 風險 |
|---|---|---|
| 備份內容 | `scripts/backup.sh`／`deploy/host-backup.sh`：`pg_dump` 自訂格式、**整個資料庫**，含 `collaboration_recipients`（收件人、電話、地址）；檔案權限 600 | 備份包含個資 |
| 備份保存期 | 預設 `KEEP_DAYS=30`（過期檔以 `find -mtime +N -delete` 刪除）；異地備份與加密由 Owner 提供儲存（W-27） | 清除後的個資仍會留在備份裡直到備份過期；異地副本的保存期**未知** |
| 最長暴露時間 | 即使遵守政策：個資最晚於核准後 90 天（履約延後時最晚 180 天）被清除，再加 **最多 30 天**的備份保存期 | 一般情況約 120 天、最壞約 210 天 |
| 還原風險 | 從備份還原會把**已清除的個資帶回來** | 清除是「資料庫狀態」，不會自動回溯到備份 |

**建議（請 Owner 決策，見 §8）**
1. **採用「備份自然過期」作為到期處理**，並把「最長暴露 ≈ 保留期＋備份保存期」寫進對團主的隱私告知（現況，無須開發）。
2. **還原後一律先清除再開放**：任何還原（含還原演練、災難復原）完成後，**先在隔離環境**執行 `npm run collab:purge`（試跑確認，再 `--execute`），確認 `/collaboration/retention` 沒有警示，才把資料庫交付使用。本 PR 已提供腳本與狀態頁；`docs/BACKUP_RESTORE_RUNBOOK.md` 已補上此步驟。
3. **縮短備份保存期**：若要把最壞暴露時間壓到約 190 天以內，把個資所在資料庫的 `KEEP_DAYS` 降到 14 天（代價：可回溯的時間變短，RPO 不變）。
4. **異地備份**：必須設定與本機相同或更短的保存期，並加密；保存期未確認前，不得把真實個資放進系統。
5. **（較大改動，未做）欄位層級加密＋銷毀金鑰（crypto-shredding）**：個資欄位以專用金鑰加密，到期銷毀該期金鑰，備份中的密文即永久不可讀。成本高，建議在資料量與法遵要求明確後再評估。

### 7.5 D-44：廠商對外入口安全 Gate（技術檢查與證據）

> 全部由自動化測試在**隔離的測試資料庫**執行（`tests/collaboration-hardening.test.ts`、`tests/collaboration-rbac.test.ts`、`tests/security-fuzz.test.ts`、E2E）。✅＝通過；⚠️＝通過但有範圍限制。

| # | 檢查 | 結果 | 證據 |
|---|---|---|---|
| 1 | 未登入＝401 | ✅ | 7 條敏感端點全部 401 |
| 2 | 無權限＝403 | ✅ | 廠商、團主、小編呼叫指派、保留、清除端點全部 403；財務不洩漏存在性（404） |
| 3 | 跨組織／跨廠商／跨團主＝404，與不存在的 id 回應一致 | ✅ | 詳情、收件資料、交接紀錄三條路徑真實 id 與假 id 狀態碼與錯誤碼相同；跨組織管理者對指派、保留例外也是 404 |
| 4 | Session 與 CSRF | ⚠️ | 登出後 token 立即失效；Cookie 為 HttpOnly＋SameSite；寫入請求的 `Origin` 與 `Host` 不符＝403（已驗證寫入沒發生）。**沒有 CSRF token**：防護靠 SameSite Cookie＋Origin 檢查，這對現代瀏覽器足夠，但舊瀏覽器或跨子網域場景不在驗證範圍 |
| 5 | IDOR | ✅ | 同上＋全路由模糊測試（6 角色 × 假／真 id × 壞 body／壞 query）無 5xx；SF-3 為本輪發現並修正的真實 IDOR |
| 6 | 個資存取範圍：廠商只取得自己負責且仍在履約期限內的收件資料 | ✅ | 履約視窗開著才給；寄出、暫緩、結案、未確認、超過硬性上限都拒絕；補寄建立後重新開啟；別家廠商 404；每次讀取寫稽核（用途 `VENDOR_FULFILMENT_EXCEPTION`） |
| 7 | 惡意 CSV 與公式注入（匯入、匯出兩邊） | ✅ | 匯出補單引號；匯入偵測公式列並擋下；電話 `+886…` 不誤判 |
| 8 | 匯入重複請求 | ✅ | 同檔重送 409；兩個並行 commit 合計只建立 1 筆 |
| 9 | URL 安全 | ✅ | `javascript:`、`ftp:`、內嵌帳密一律 422（建立端）或不保存（匯入端） |
| 10 | Rate limit | ⚠️ | 個資讀取、匯出、匯入皆有上限且回 429；**限流在單一程序記憶體**（既有 K3／W-26），多實例部署需改共用儲存；IP 取自 `X-Forwarded-For`（既有 O2） |
| 11 | 操作稽核 | ✅ | 指派、交接、保留例外、清除、匯出（含 `piiMode`）、個資讀取全部寫稽核；稽核與事件內容不含個資（哨兵掃描） |
| 12 | 權限變更後立即失效 | ✅ | 撤銷廠商範圍、承辦人被換掉、角色降級、停用帳號，**下一個請求就生效**（每個請求都重新讀使用者與範圍，不快取） |
| 13 | 廠商匯出不含個資、無法由其他端點取得 | ✅ | 廠商表單二不存在收件人／電話／地址欄位；掃過團主與廠商可呼叫的 19 條讀取端點（列表、總覽、搜尋、匯出、主檔面板、匯入列、稽核、通知、事件歷程）都不含哨兵字串；以個資內容搜尋找不到案件 |

**Gate 結論**：技術檢查在 DEMO／測試環境**通過**。**但仍不得向正式外部廠商開放入口**，因為下列條件尚未滿足（需 Owner 或部署環境處理，見 §8 與 `docs/KNOWN_ISSUES.md` W-35、W-41～W-48）：
1. 沒有部署到任何主機，**真實 HTTPS、反向代理對 `X-Forwarded-For`／`Origin` 的處理、多實例限流**都沒有在真實環境驗證；
2. D-40 政策數字（90／30／180 天、被拒案件的保留）尚待 Owner 確認；備份保存期與異地備份未確認；
3. Repo 仍是 Public（D-43），且 Owner 尚未做 §REPO_SECURITY_REPORT 的操作；
4. 沒有第三方滲透測試，也沒有對廠商帳號開通流程（誰建帳號、如何綁定 `vendor_id`、如何撤銷）的書面作業程序；
5. 沒有 MFA（既有 K1）——廠商帳號可讀取收件個資，建議開放前至少要求強密碼與 MFA 評估。
