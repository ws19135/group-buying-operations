## ADR-001 技術棧
- **脈絡**：藍圖 §8.1 建議「模組化單體＋背景工作佇列＋關聯式資料庫」，§8.2 把技術棧列為待決策。招財兔系統是 Apps Script＋Sheets。本儲存庫開工前**沒有任何程式碼**，所以沒有「延續既有框架」的選項；對招財兔系統則有遷移成本。
- **決策**：Next.js 15（App Router）＋TypeScript 5.9＋PostgreSQL 16；後端是同一個 Next 專案內的 `src/server/**` 服務層（框架無關），API 為單一路由表（`src/server/api`）；背景工作用獨立的 Node worker（`scripts/worker.ts`）。
- **為何不延續 Apps Script**：(1) 招財兔的缺口分析顯示權限無法在後端強制、沒有版本控制／自動化測試／備份（它的 G-08、G-16、G-17、G-19）；(2) 本系統要多團主／多廠商資料隔離與交易一致性，試算表做不到；(3) 評估過的遷移成本（見 ADR-019）是「不遷移、只對照」，所以沒有替換成本。
- **後果**：需要自行維運資料庫與部署（見 DEPLOYMENT.md）。Google Sheets／Apps Script 相容層列為 `PROPOSED`，目前以 CSV 匯入匯出作為相容路徑。
- **推翻成本**：高（整個專案）。
- **Owner 確認（2026-10-29）**：公司有 IT 或預算可以維運主機，且長期會放真實資料 → **維持此技術棧，不改用 Apps Script 重寫**。部署位置（Render 雲端主機或公司主機）尚待決定；Google Sheets／Apps Script 維持「匯入匯出的相容橋」角色。
- **決策程序的修正**：本決策原先由我提出後直接建置，沒有在動工前說明「需要自行維運主機」的代價。往後凡是會改變**技術棧、部署方式、公開範圍、需要使用者自行維運**的決定，一律先講清楚再做。

## ADR-002 資料庫存取與 migration
- **決策**：`pg` + 手寫 SQL migration（`migrations/*.sql`，依檔名順序，記錄 checksum；已套用的檔案被改動會被擋）。不用 ORM，因為約束、觸發器、部分唯一索引（防重複、軟刪除）是核心保證，直接寫 SQL 最透明；也避免在受限網路下下載 ORM 引擎。
- **後果**：型別由 zod schema 與手寫 interface 維護；新增欄位一律新增 migration。

## ADR-003 多租戶與資料隔離
- **決策**：每張業務表帶 `organization_id`；所有查詢帶組織條件；Campaign 相關資料一律經 `campaignScope(actor)` 取得可見範圍（`src/server/lib/scope.ts`）。測試以「每個測試檔一個獨立組織」進行，並有跨組織讀／寫測試。
- **後果**：未使用 PostgreSQL Row-Level Security（RLS）；隔離靠服務層＋測試。若日後要更強的保證可加 RLS（`PROPOSED`）。

## ADR-004 八階段生命週期與 SOP 映射（找不到規格，自行定義）
- **脈絡**：任務要求「依 ERP 八階段生命週期重新整理」，但藍圖只有 12 階段流程與 13 種狀態，沒有「八階段」。
- **決策**：定義 8 個任務階段（`workflow_template_steps.phase`）：1 籌備與寄樣、2 試用與回饋、3 開團審核、4 素材與賣場準備、5 開團與曝光、6 銷售與催單、7 結單與請款、8 復盤與結案。SOP 11 步全數保留（寄樣、到貨試用、回饋、開團審核、回收、圖文、開團、Live Talk、話題、催單、結算＋請款），另依藍圖補 G2（開團前檢查）、G3（結單核對）、G5（復盤結案）三個關卡任務與「結算」「請款」拆成兩步，共 **15 步**。對照見 [WORKFLOW_MAPPING.md](WORKFLOW_MAPPING.md)。
- **推翻成本**：低（模板是資料，改成新版本即可，既有檔期不受影響）。

## ADR-005 角色、權限與資料範圍
- **決策**：6 個角色：`SYSTEM_ADMIN`、`OPS_MANAGER`、`OPS_EDITOR`（藍圖的「營運 PM」＝任務的「營運小編」）、`HOST`、`VENDOR`、`FINANCE`。客服／稽核唯讀（藍圖有、任務沒列）**未做**。權限 43 項（Phase 1 為 34 項，Phase 2 新增履約、售後、財務共 9 項）（`src/server/lib/permissions.ts`），一人一個角色。
- **資料範圍**：管理者／營運主管／財務＝整個組織；營運小編＝自己負責或被指派任務的檔期；團主＝自己被邀請（未婉拒）的檔期，且只看到自己的團主資料、自己的目標、HOST 角色的任務；廠商＝自己廠商的商品與檔期、VENDOR 角色的任務。外部角色看不到其他人是否存在（回 404）。
- **敏感欄位**：商品成本只給管理者／營運主管／財務；檔期目標與內部備註只給內部角色；佣金規則只有管理者與財務可寫，團主只讀自己的。
- **預設的待決策答案**：團主「看不到」成本與淨利，只看到自己的預估佣金；營運小編不可覆寫金額。
- **推翻成本**：中（權限表與測試需調整）。

## ADR-006 認證
- **決策**：Email＋密碼（scrypt）、HttpOnly＋SameSite=Lax cookie、12 小時 session（資料庫只存 token 的 sha256）、5 次失敗鎖 15 分鐘、IP／帳號限流、停用帳號立即撤銷 session、寫入類請求檢查 Origin 與 Content-Type。
- **未做（需 Owner 決定）**：SSO／OAuth、MFA（藍圖 §8.3 要求管理者啟用 MFA）。限流為單機記憶體，多實例部署需改共用儲存。

## ADR-007 稽核與軟刪除
- **決策**：`audit_logs` 以資料庫觸發器禁止 UPDATE／DELETE；所有業務表以觸發器禁止 DELETE（錯誤碼 `restrict_violation`），一律用 `deleted_at` 或狀態欄軟刪除；**API 沒有任何 DELETE 方法**。稽核記錄含操作者、角色、來源（WEB/API/WORKER/SEED）、request id、前後值、原因。
- **取捨**：`sessions`、`idempotency_keys` 允許刪除（暫存性質）。

## ADR-008 狀態機與 Gate
- **決策**：14 種狀態（藍圖 13 種＋暫緩）。轉移分三類：`MANUAL`（一般變更）、`GATE`（只能經核准流程）、`AUTO`（worker）。倒退必須填原因並自動取消待核准申請。G1／G2 申請時狀態先進入「待選品核准／待開團核准」；G3–G5 維持原狀態直到決定。每個 Gate 有系統檢查（BLOCK 必須通過，WARN 只提醒），核准時重新檢查。G2 的「高風險衝突」可由核准者填寫風險確認原因後放行（原因進稽核）。進入履約後不可取消（退款／售後屬 Phase 2）。
- **核准者**：G1/G2/G5＝管理者、營運主管；G3＝管理者、營運主管、財務；G4＝管理者、財務。可用組織設定 `approval.require_distinct_actor=true` 要求申請人≠核准人（預設關，小團隊可能同一人）。

## ADR-009 排程引擎
- **決策**：起始日＋天數；**結束日＝開始日＋天數−1（含頭尾）**，下一步＝前一步結束日＋1（與 SOP 一致）。起算規則三種：檔期欄位＋位移、接在某步驟後、接在多個步驟後。條件不成立的步驟建為 SKIPPED 且不參與排程，相依它的步驟「穿透」到更前面的步驟。人工調整單一任務日期＝鎖定（需原因），重排不得覆寫；已完成任務不重排。
- **預覽後確認**：日期／天數／條件變更必須先預覽（逐任務前後值、被鎖定而未動者、衝突），確認時帶預覽代碼（hash）；預覽後有任何變動則代碼失效。已排程／進行中的檔期改日期必須填原因且限管理者／營運主管；進行中不可改開團日。
- **模板版本化**：修改預設天數＝發佈新版本；檔期在建立當下保存模板版本與參數快照，**不會被新版默默改寫**。

## ADR-010 KPI 口徑（單一來源：`src/server/lib/kpi.ts`）
- 計入銷售：`PAID`、`PARTIAL_REFUND`、`REFUNDED`（`PENDING` 未付款、`CANCELLED` 不計）。GMV＝Σ 訂單金額；有效淨銷售額＝GMV−退款；有效訂單數＝PAID＋PARTIAL_REFUND；AOV＝淨銷售÷有效訂單；退款率＝有退款訂單÷計入銷售訂單；達成率＝淨銷售÷目標（目標空或 0 → 顯示「—」不顯示 0%）。
- **期間**：以下單時間（台北日曆月）。**歸因**：訂單可歸因到一位或多位團主（share_percent）；未歸因金額在管理端明列。**目標達成率**：與本期重疊且設有目標的檔期，累計淨銷售÷目標合計。
- 管理端與團主端用同一份定義，測試驗證兩邊同一團主的數字相等。

## ADR-011 訂單匯入與 DEMO
- **決策**：CSV（每列＝一個品項，同 `source_order_id` 合併）。同檔（sha256）只能匯入一次；跨檔以 (來源, 來源訂單編號) 去重，內容相同略過、退款／狀態變動則更新並稽核、品項被改進錯誤佇列；問題列進 `import_errors`，不阻擋其餘列。不存姓名／電話／地址，只存去識別化的 `buyer_ref`。下單時間：`YYYY-MM-DD HH:mm`（視為台北時間）或含時區的 ISO；無時區的 `T` 格式拒絕（有歧義）。
- **DEMO**：`data_origin=DEMO` 只能由種子程式（`actor.source=SEED`）寫入；Dashboard 偵測到 DEMO／混合時顯示醒目橫幅。沒有任何訂單時顯示「待串接」，KPI 為 null（顯示「—」）。
- **BLOCKED**：電商 API／Webhook（缺平台與憑證）。

## ADR-012 自動化
- **決策**：所有工作預設停用（`automation_settings`）；worker 需 `AUTOMATION_ENABLED=on` **且**該工作被啟用；每次執行寫 `automation_runs`（冪等鍵、嘗試次數、統計、錯誤）；失敗最多重試 3 次；通知走佇列＋Adapter，**目前只有測試 Adapter**，站內通知（IN_APP）直接送達，EMAIL／LINE 只進測試 Adapter；Adapter 失敗不影響主流程，3 次後標 DEAD 並建立例外。自動化不修改財務與合作條件（進件的分潤％只寫在備註，不寫入佣金規則）。

## ADR-013 佣金與結算
- **決策**：Phase 1 只做「預估佣金」＝歸因有效淨銷售額×費率（費率規則版本化：檔期專屬優先於團主預設；沒有規則就顯示「尚未設定」，不猜）。`settlements`／`settlement_items` 只建 Schema。**不套用招財兔的分潤公式**（藍圖 §1.5：不把招財兔內部帳務擴張到所有群組）。
- **需 Owner 確認**：團主佣金基礎（淨銷售？含稅？扣費用？）、四捨五入、是否需雙人覆核。

## ADR-014 ID
- **決策**：業務 ID 即主鍵（`VEN-0001`、`OWN-0001`、`GRP-0001`、`PRD-000001`、`SKU-000001`、`CMP-YYYYMM-0001`、`TSK-YYYYMMDD-0001`…），由資料庫計數器原子遞增產生，不依名稱／列號。

## ADR-015 冪等性
- **決策**：建立類 API 支援 `Idempotency-Key`（同一交易內寫入鍵與結果，並發請求等待後取得同一結果）；沒有 key 時以自然鍵（正規化名稱、統編、廠商＋標題＋開團日…）的部分唯一索引擋下並回報既有 ID；自動化以 (工作, 冪等鍵) 唯一；匯入以檔案 checksum＋來源訂單編號。

## ADR-016 時間
- **決策**：日期（開團日等）存 `date`，伺服端以 `YYYY-MM-DD` 字串處理（避免時區位移）；時間戳存 `timestamptz`；組織時區 `Asia/Taipei`；「今天」一律以台北日曆日。

## ADR-017 前端
- **決策**：伺服器元件直接呼叫服務層（同一套授權），互動以 client component 呼叫 `/api`；純 CSS，不引入 UI／圖表套件；所有主要元素有 `data-testid`。後端永遠重新授權，前端隱藏只是體驗。

## ADR-018 測試
- **決策**：整合測試使用**真實 PostgreSQL**（`erp_test`，每次重建 schema），每個測試檔建立獨立組織，可平行；純函式（排程、KPI、狀態機、CSV）另有單元測試；E2E 煙霧測試用 Playwright。測試結果以指令與退出碼記錄（TEST_REPORT.md）。

## ADR-019 與既有系統的關係
- **決策**：不連線、不修改、不遷移招財兔系統與任何 Google 資料。僅提供「概念對照」（例如：招財兔 11 種狀態 → 本系統 14 種狀態，並不 1:1）與 CSV 匯入作為過渡期的資料進入方式。招財兔已核准的規格（分潤公式、財務模組）不被本系統改寫。
- **需 Owner 確認**：過渡期哪個是主系統（藍圖待決策 #6）、歷史資料遷移範圍（#5）。
